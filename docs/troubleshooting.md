# Argus Sensor Troubleshooting Guide

**Status:** Verified against source.
**Scope:** Argus sensor only (`~/Saber/argus/argus`). Issues specific to client programs (`ra`, `radump`,
etc.) are out of scope — see the note at the end of each relevant section.
**Supersedes:** the previous version of this document, which contained numerous incorrect or unconfirmed
CLI flags (`-V`, `-W`, `-M cpu`, `-S <host:port>`, `-D filter`/`-D output`), non-existent config variables
(`ARGUS_MAX_FLOWS`, `ARGUS_OUTPUT_BUFFER`, `ARGUS_LOG_SYSLOG`), an incorrect config search-path list, and
several client-side tool invocations that reference commands not confirmed to exist. Every specific
correction is called out inline below.

---

## Installation Issues

### Problem: `./configure` fails — `libpcap not found`

```bash
# Ubuntu/Debian
sudo apt-get install libpcap-dev
# Fedora/RHEL
sudo dnf install libpcap-devel
# macOS
brew install libpcap
```

```bash
./configure --with-pcap=/usr/local
```

This guidance is standard `autoconf`/libpcap practice and was not specific to a fabricated claim — retained
as-is, though the exact `configure` flag name was not individually re-verified against `configure.ac` for
this pass.

### Problem: `make` fails — missing `argus_config.h`

```bash
./configure
make
```

Standard autotools behavior — `argus_config.h` is generated by `./configure`. Accurate as general guidance.

### Problem: `make install` — permission denied

```bash
sudo make install
# or:
./configure --prefix=$HOME/.local && make && make install
```

Accurate as general guidance.

## Capture Problems

### Problem: No packets captured

```bash
ip link show eth0          # confirm interface exists and is up
sudo tcpdump -i eth0 -c 10 # confirm traffic actually reaches the interface
```

```bash
sudo setcap cap_net_raw,cap_net_admin=eip $(which argus)
# or run as root:
sudo argus -i eth0
```

This part of the previous doc was reasonable general libpcap-capture guidance and is retained; the
capability-setting command was corrected to use `$(which argus)` rather than a hardcoded
`/usr/local/sbin/argus` path, since install location depends on `--prefix`.

### Problem: `pcap_activate failed: Operation not permitted`

```bash
sudo argus -i eth0
# or, on Linux:
sudo setcap cap_net_raw,cap_net_admin+eip $(which argus)
```

Also check AppArmor/SELinux if capture still fails after granting capabilities — this is standard Linux
guidance, not specific to Argus, retained without additional source verification.

### Problem: Filter doesn't work as expected

**Dump the compiled filter (confirmed real flag):**
```bash
sudo argus -i eth0 -b 'tcp port 80'
```
`-b` is confirmed at `argus/argus.c:114` / `Argusbpf_dump` (`ArgusSource.c:5549`) — it dumps the BPF filter
compiler output, which is the correct way to debug a filter expression that isn't matching what you expect.

**Compare against tcpdump using the same expression:**
```bash
tcpdump -i eth0 'tcp port 80' -c 10
```
Since Argus compiles filters via the same libpcap `pcap_compile()` call tcpdump uses (`ArgusSource.c:1063`),
if tcpdump matches the traffic you expect but Argus doesn't, the filter expression itself is not the
problem — look at interface selection or `-e`/monitor-ID configuration instead.

**Quoting:** always quote multi-word filter expressions to avoid shell word-splitting:
```bash
argus -i eth0 'tcp port 80'      # correct
argus -i eth0 tcp port 80        # wrong — shell splits this into separate argv entries
```

*(Removed: the previous doc's "common filter mistakes" example claimed `'tcp and port 80'` was wrong and
`'tcp port 80'` was the fix — this is not a documented Argus/BPF filter distinction; both are valid BPF
syntax with different (correct) semantics, `tcp and port 80` matches TCP traffic on port 80 in either
direction, `tcp port 80` is typically equivalent. This wasn't a real "mistake" pattern and has been
dropped rather than propagated.)*

### Problem: High packet loss

```bash
# Increase kernel-level socket buffer limits (Linux)
sudo sysctl -w net.core.rmem_max=134217728
sudo sysctl -w net.core.rmem_default=134217728
```

This is standard Linux kernel tuning guidance for high-volume packet capture generally, not
Argus-specific, and was not independently re-verified against this codebase — retained as reasonable
general advice for context, not as a documented Argus feature.

**Increase the pcap capture buffer directly (confirmed real config variable):**
```conf
ARGUS_PCAP_BUF_SIZE=1G
```
Confirmed in `man/man5/argus.conf.5` and `ArgusResourceFileStr[]` — accepts `K`/`M`/`G` suffixes. See
`docs/configuration.md`.

*(Corrected: the previous doc suggested `taskset -c 0 argus -i eth0` for CPU pinning as an Argus-specific
recommendation. CPU pinning via `taskset` is a generic OS mechanism, not an Argus feature or documented
recommendation — retained only as a generic OS-level option, not as something Argus itself controls.)*

## Configuration Issues

### Problem: Configuration file not read

**Check the only automatically-searched location:**
```bash
ls -la /etc/argus.conf
```

*(Corrected: the previous doc instructed checking `$ARGUSPATH/argus.conf` and `$HOME/argus.conf` as
additional auto-searched locations. **Confirmed there are none** — a full-repo search for `getenv()` in
`argus.c`, `ArgusSource.c`, and `ArgusUtil.c` returns zero results, and the man page for `argus.conf`
explicitly documents `$ARGUSPATH`/`$ARGUSHOME`/`$HOME` search as deprecated from earlier versions.
`/etc/argus.conf` is the only file the sensor loads automatically, and only if it exists — see
`docs/architecture.md` §7 and `docs/configuration.md` §2.)*

**Load an explicit config file instead:**
```bash
argus -F /path/to/argus.conf -i eth0
```

**Check syntax — no spaces around `=`:**
```conf
ARGUS_DAEMON=yes    # correct
ARGUS_DAEMON = yes  # wrong
```

**Check variable names against the verified list** in `docs/configuration.md` §3 — a typo'd or
non-existent variable name is silently ignored by the config parser, not flagged as an error you'd
necessarily notice.

### Problem: Interface not found

```bash
ip link show
# or
ifconfig -a
```

```bash
argus -i all
```

*(Corrected: `all` used bare — as opposed to a more specific form — is a real, minimal way to reference
every interface, but note the richer syntax in `docs/configuration.md` §4, e.g. `-i ind:all` for
independent per-interface tracking. `argus -i all` without the `ind:`/`dup:`/`bond:` prefix uses whatever
Argus's default combination behavior is for multiple interfaces — this default behavior was not
independently re-verified in this pass; if it matters for your deployment, confirm explicitly with
`-i ind:all` rather than relying on unqualified `all`.)*

### Problem: Output file not created

```bash
ls -ld /var/log/argus/     # writable by the argus user?
df -h /var/log/            # disk space?
```

```bash
# Use an absolute path
argus -i eth0 -w /var/log/argus/data.argus
```

```bash
# Write to stdout to confirm the sensor is producing output at all
argus -i eth0 -w -
```

*(Corrected: the previous doc used `-W -` for "write to stdout." **There is no `-W` flag** — confirmed
against the real optstring (`argus.c:451`). Stdout output is `-w -`, using the same `-w` flag as file
output, per the usage text at `argus.c:162`.)*

## Performance Problems

### Problem: High CPU usage

**Simplify the capture filter** to reduce per-packet processing:
```bash
argus -i eth0 'tcp or udp'
```

**Reduce flow-key complexity** if using an expanded key:
```conf
ARGUS_FLOW_KEY=CLASSIC_5_TUPLE
```

*(Corrected: the previous doc's `-M cpu` "self-monitoring" flag does not exist. **`-M <secs>` sets the MAR
(management/status record) report interval in seconds** (`argus.c:528`, confirmed default 300s at
`argus.c:143`) — it is not a monitoring-mode selector. MAR records do contain sensor health/performance
data (packet counts, drops, queue depth — see `docs/data-model.md` §6), so `-M <secs>` is the right lever
for *how often* that health data is emitted, but there's no separate "cpu mode.")*

*(Also corrected: `-S 10` for "sample every Nth packet" does not exist. **`-S <secs>` sets the flow-status
report interval** (`argus.c:578`, default 60s) — same family of confusion as `-M`, no sampling behavior is
implied by either flag.)*

### Problem: Memory exhaustion

```conf
# Reduce how long idle flows are retained in the flow cache
ARGUS_TCP_TIMEOUT=60
ARGUS_IP_TIMEOUT=30
```

*(Corrected: the previous doc's `ARGUS_MAX_FLOWS=1000000` and `ARGUS_FLOW_TIMEOUT=300` do not exist as
config variables. **There is no direct flow-count cap.** Memory pressure from flow-table growth is
controlled indirectly via the per-protocol timeout variables (`ARGUS_IP_TIMEOUT`, `ARGUS_TCP_TIMEOUT`,
etc. — full list in `docs/configuration.md` §3) and `ARGUS_HASHTABLE_SIZE`, which affects lookup
performance rather than a hard memory ceiling.)*

```bash
# Check for actual memory leaks (generic tool, not Argus-specific)
valgrind --leak-check=full argus -r test.pcap
```

### Problem: Slow output writing

```bash
argus -i eth0 -w argus-udp://collector.example.com:561
```

*(Corrected: the previous doc suggested `-S localhost:5100` for "asynchronous socket output" — **neither
the flag semantics nor the port number are correct.** `-S` is the status-interval flag (see above); remote
streaming output uses `-w argus-udp://host[:port]` (default port **561**, not 5100 — confirmed at
`argus.c:159` and `include/argus_int.h:68`, `#define ARGUS_PORT 561`). See `docs/architecture.md` §6 and
`docs/configuration.md` §3 (`ARGUS_OUTPUT_STREAM`) for the two real remote-output mechanisms.)*

*(Removed: `ARGUS_OUTPUT_BUFFER` and general output-stream gzip compression via a shell pipe
(`argus -w - | gzip`) — the first variable doesn't exist; the second is technically possible as a shell
trick but was presented as an Argus feature, which it is not. See `docs/architecture.md` §6: the sensor
has no built-in output compression.)*

## Output/Data Issues

**This section is now scoped to sensor-side causes only.** Interpreting/reading flow record content
requires client tools (`ra`, `radump`) from the separate `~/Saber/argus/clients` repo, which is out of
scope for this document — see `docs/data-model.md`'s scope note for why. If flow records look wrong,
first isolate whether the problem is in the sensor's classification/capture (in scope here) or in a
client's interpretation of the record (out of scope here, check the clients repo).

### Problem: Suspected wrong byte counts / missing timestamps / wrong protocol detection (sensor side)

**Confirm packets are actually being captured correctly, independent of Argus:**
```bash
sudo tcpdump -i eth0 -c 100 -w test.pcap
```
Then feed the same pcap to Argus (`-r test.pcap`) and compare — if Argus's classification of that exact
packet capture looks wrong, that's a sensor-side (in-scope) issue; if raw capture itself looks wrong,
that's an OS/interface/tcpdump-level issue, not Argus.

**Check flow directionality setting:**
```conf
ARGUS_FLOW_TYPE=Uni
```
*(Corrected: previous doc's `argus -i eth0 ARGUS_FLOW_TYPE=Unidirectional` is not valid command-line
syntax — `ARGUS_FLOW_TYPE` is a config-file variable, with no command-line-flag equivalent, confirmed in
`man/man5/argus.conf.5` under `ARGUS_FLOW_TYPE`. Set it in a config file loaded via `-F`, not as a bare
command-line token.)*

### Problem: Missing metrics in output (sensor side)

Several metrics require an explicit feature toggle in `argus.conf` before the sensor will generate them at
all — confirmed real variables (see `docs/configuration.md` §3 for the complete list):

```conf
ARGUS_GENERATE_JITTER_DATA=yes
ARGUS_GENERATE_APPBYTE_METRIC=yes
ARGUS_GENERATE_MAC_DATA=yes
```

*(Corrected: previous doc's `ARGUS_ENABLE_JITTER_METRICS=yes` uses the wrong variable name — the real
variable is `ARGUS_GENERATE_JITTER_DATA`.)*

If a metric is still missing after confirming the right toggle is set, the next thing to check is whether
the metric is even applicable to the flow's protocol — see the "Produced by: Sensor" column in
`docs/data-model.md` §4 for which DSRs exist for which protocols.

## Debugging Tools

### Argus debug output

```bash
argus -i eth0 -D 3
```

`-D <level>` is a purely numeric debug level, parsed with `atoi()` (`argus.c:467`,
`setArgusdflag(ArgusModel, atoi(optarg))`) and only available if the sensor was built with `ARGUSDEBUG`
defined (`argus.c:120`).

*(Corrected: the previous doc's `-D filter` and `-D output` (non-numeric "component" debug modes) do not
exist. `atoi("filter")` evaluates to `0`, so passing a non-numeric string to `-D` silently sets debug
level 0 rather than enabling any component-specific debug mode.)*

### System-level debugging (generic, not Argus-specific)

```bash
strace -f -p $(pidof argus)      # Linux
dtruss -p $(pidof argus)          # macOS
```

Retained as standard OS-level diagnostic technique — not verified as Argus-specific since it isn't.

### Checking what the sensor is listening on

```bash
netstat -an | grep 561
```

*(Corrected: previous doc's example used port 5100 throughout, including in a `tcpdump -w argus_debug.pcap
'port 5100'` example. **The confirmed default port is 561**, not 5100, for both `-P <portnum>` remote
access and the default `argus-udp://` stream port — see `docs/configuration.md` §3, `ARGUS_ACCESS_PORT`.)*

## Common Error Messages

| Symptom | Likely cause | Where to look |
|---|---|---|
| `pcap_activate failed: Operation not permitted` | Missing packet-capture privilege | §"Capture Problems" above |
| Interface not found | Wrong name, or OS renamed it | `ip link show` / `ifconfig -a` |
| Sensor exits immediately with usage text | Unrecognized flag (e.g. `-V`, `-W`, `-M cpu`) passed | Re-check flag against `argus -h` output or `docs/configuration.md`/this doc's corrections |
| Config values not applied | Typo'd variable name, or expecting env-var/`$HOME` config support that doesn't exist | §"Configuration Issues" above |
| `Can't bind` / port in use | Another process (or another `argus`/`radium` instance) already on that port | Check `ARGUS_ACCESS_PORT`, use `-P <other-port>` |

*(Corrected: the previous doc's error table included `File format error → version mismatch` and
`Filter compile error → invalid syntax` framed around client-tool (`ra`) interoperability — that class of
issue is real but belongs to a client-side troubleshooting doc, not this sensor-focused one.)*

## Getting More Help

```bash
uname -a
argus -h            # NOT -V, see correction above
cat /etc/os-release
```

```bash
cat /etc/argus.conf
```

*(Corrected: previous doc suggested `argus -F /etc/argus.conf -V` to "validate" a config — `-V` isn't a

running with a high debug level in the foreground: `argus -F /etc/argus.conf -D 3 -d` and observing
startup log output.)*
